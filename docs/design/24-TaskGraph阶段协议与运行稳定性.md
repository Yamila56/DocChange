# TaskGraph：阶段协议与运行稳定性

2026-11-17。策略仍为 `taskgraph-v2`，持久协议版本为 `maintenance-v2h4`。本次在新的公开任务批次开始前修复协议与执行缺陷，不加入动态重规划或扩展检索。

## 已确认与已修复

| 问题 | 代码核验与处理 |
|---|---|
| 阶段共用超集 Schema | 拆成 PlanDecision、ProposeDecision / NoChangeDecision / UnresolvedDecision、ReviewDecision 的通过/缺陷分支；REPAIR 使用独立的局部修补协议。Prompt、发送的 Schema 和本阶段解析使用同一个协议映射。必填说明与依据不再默默补为空值；非空编辑、空no_change编辑及review的ready/defects约束也直接体现在JSON Schema中。 |
| 首次格式错误即失败 | 每阶段最多一次结构化纠错，保留原响应与错误；补问同样预留模型调用，计入原总预算。JSON/Schema 以及限定的引用完整性错误可以纠正；超时、未知数据库故障、无依据和复核持续不通过不无限重试。 |
| 引用领域适配缺失 | 上层任务/实现依据与仓库观察分开；候选保留完整引用，Git工具只接收已校验仓库观察。编辑/覆盖格的完整引用仍保留，未知来源仍拒绝。 |
| 修补权限检查过宽 | 多需求编辑要求每个需求/路径均获准；未被缺陷点名的覆盖格必须保持不变。仍只有一轮语义修补。 |
| SQLite 并发写入 | 本地短事务使用 BEGIN IMMEDIATE，避免读取租约/事件号之后并发升级写锁；配置有限 busy_timeout，仅对已回滚的 SQLITE_BUSY/MySQL 锁错误重试。模型、检索与外部 I/O 仍在事务外。MySQL 行锁、fencing 和权限校验保留。 |
| 心跳异常传播 | 心跳故障转换为该任务的 LEASE_HEARTBEAT 错误；用户取消和截止时间仍保留取消语义，避免一个任务的心跳取消整个评测控制器。 |
| 取消后的索引线程 | 同一环境及浅拷贝共享取消事件，文件访问和索引遍历检查停止信号；Python 线程正在执行的单次计算不可强杀，不宣称即时取消。 |
| 重启重置时间窗 | 新运行以整数毫秒保存绝对截止时间和耗时，避免MySQL JSON浮点往返改变检查点哈希；恢复沿用原期限；超期不重新获得一轮执行窗口。此仓库流程无人工等待中的在线模型循环。 |
| Windows 摘要文件替换失败 | 报告和 JSONL 使用唯一临时文件、原子替换及有界共享冲突重试；失败时保留上一份完整文件，不留下半份有效报告。评分只改变工件写入方式，官方准则、证据校验与数值评分不变。 |

## 并发与资源边界

共享索引保护改为按 docs/code 根目录分别加锁：不同根可以重叠执行，同一根的初始化与搜索仍互斥。每个事件循环跨运行最多两个冷实现索引构建；已经构建的索引查询和文档搜索不占该槽位，避免8个大代码语料同时占内存。并发读取继续使用隔离观察集合，结果在事件循环中合并；这不等于同一索引或 GPU 推理的并行加速。DISCOVER 完成后释放不再使用的内存索引，持久工具回执和证据仍保留。

新增发现总耗时、逐工具耗时、缓存复用与搜索锁等待记录。模型调用数和端到端耗时分别报告，不能把提前失败造成的低调用数解释成效率收益。

## 本次不改变的设计与风险

- 每个任务初步批读最多 2 个文档路径、2 个实现路径，每个最多 120 行；搜索片段也是已观察证据。这个上限不代表完整覆盖，`exhaustive_repository_coverage` 仍为 false。
- 不新增维护任务、不加入 VERIFY→REPLAN，不扩大 K、不换 embedding/reranker。计划遗漏与发现不足仍需逐题证据区分，不能把所有缺失路径归因于检索。
- 图是 provenance / evidence relation graph，用于关联、校验和审计；没有图检索或知识图谱推理。
- 独立上下文 Reviewer 仍会误判。失败候选可另行交官方裁判诊断，结果与最终预测分开；诊断高分不能把未交付候选改算成成功，拒绝本身也不证明误拒。
- 不兼容的旧 TaskGraph 检查点拒绝续跑；旧试跑与新协议使用不同批次，费用、原始响应和故障证据均保留。

## 验证和评测

本轮工程验证见[硬化记录](../evaluation/taskgraph-hardening-2026-11-17.md)。工程检查证明上述边界，不是模型质量成绩。

新批次固定原 49 题，对比历史 coverage-v1 Flash。保持请求模型、检索配置、32 次调用上限、180 秒请求、1800 秒任务、8 个任务并发以及官方评分规则。协议与 Harness 修复属于新版整体的一部分，历史比较不能单独归因于 DAG；服务端模型别名也不是不可变权重版本。

统计完成率、方向正确率、patch/no-change recall、全部需改任务的质量（执行失败保留零分）、P0-clean 交付、调用数、工具数、每 100 次调用的正确决定及耗时，附逐题配对和 A–G 失败归因。不为低分挑题或替换输出，不自动扩大至 175 题。

## 发现结果如何进入编辑上下文

证据按检索和批读顺序稳定去重。每个任务最多四份编辑依据，优先展示目标文档批读与排名靠前的文档片段。有实现检索结果时，为最相关的实现片段留一个位置。文档批读的两个名额分别给排名最高的结果与有效路径提示。精确提示优先于 glob，提示无效或与首位重合时以原排名补足。

Reviewer 仍只检查已有的需求/维护面，并读取候选引用的原文。如果编辑者漏引用已发现的反证，复核可能也会遗漏。这两处属于覆盖范围和复核输入设计，逐题证据可用于判断遗漏发生在规划、发现、编辑还是复核。

Windows 运行 DoGBench 时，本地 WSL 读取已验证实现快照，按原有文件边界向控制器传输同顺序的原文。CUDA 仍负责文档向量编码，实现索引仍用章节 BM25。DoGBench 独立输入核验确认 40 个带实现仓库的样本，其匿名 HEAD 父提交树与冻结基线一致。另 9 个样本无实现仓库。

## 运行终态与局部修补

明确证据不足和复核拒绝时，任务保存终态 `unresolved`。候选不进入待审批，旧草稿可供诊断。DoGBench 发布协议只接受 `patch` 或 `abstain` 作为完成决定，因此导出用零分失败行表示未解，并在元数据和分析表记录独立状态。评测报告同时列出任务级未解与系统异常。

修补只提交 Reviewer 指定需求和路径内的编辑以及需要更新的覆盖项。由运行时合并并保留范围外部分，再检查完整候选和覆盖。不存在明确修补路径以外的重新发现。缺少覆盖项或候选绑定不正确时允许一次纠错，仍失败则记录原因。无修改明确要求影响判断、完整支持和独立复核。规划阶段的暂定判断只能凭已观察仓库证据变更。

最终交付核对 Git HEAD、候选和覆盖/编辑/影响判断引用的原文，以及实际编辑位置。历史未引用的阅读片段不参加交付前复查。
